# ocr-bench

验证 Apple Vision (`VNRecognizeTextRequest`) 文字识别行为的命令行工具集。

## 为什么存在

PresbyFriend 的 iOS 版用 Vision 做图片 OCR。它的失败模式很隐蔽：

**`recognitionLanguages` 数组的第一个元素决定用哪个识别模型。选错则完全崩溃，
但不报错、不崩溃、不抛异常——只是安静地输出垃圾。**

实测（macOS，与 iOS 同一套 API）：

| 配置 | 中文图 | 英文图 |
|---|---|---|
| `["zh-Hans", "en-US"]` | ✅ 10/10 块正确 | ⚠️ `Tuesday` → `Tuesaay` |
| `["en-US", "zh-Hans"]` | ❌ `用法用量` → `mzms` | ✅ 正确 |
| `["en-US"]` | ❌ 同上，4 块乱码 | ✅ 正确 |
| `["zh-Hans"]` | ✅ 10/10 块正确 | ⚠️ 同第一行 |

中文模型能勉强认拉丁字母，**英文模型遇汉字直接崩**。

历史上两次「OCR 乱七八糟」都是这个成因：

- PWA MVP（`503c920`）用 Tesseract.js `chi_sim`，中文质量本就差
- Android 早期用 Latin-only 识别器硬啃中文（`4126a57` 才换成 `ChineseTextRecognizerOptions`）

**两次都是引擎选错，不是 OCR 不可行。**

另外 `.fast` 档**不支持中文**（只有 en/fr/it/de/es/pt），对中文图返回 0 个结果。
所以没有「降档换速度」的余地——必须用 `.accurate`。

设计依据见 `docs/superpowers/specs/2026-09-14-ios-v1-design.md`。

## 构建

```sh
./build.sh          # 编译到 bin/
```

需要 Xcode 命令行工具。产物在 `bin/`，不进版本库。

`ordercheck` 与 `paracheck` 例外：它们编的是 iOS 模拟器目标（原因见下），运行时需要一台
已启动的 iOS 模拟器。没有可用的 iOS 模拟器时 `build.sh` 会明确跳过它们并打印原因，
不算构建失败。

**编出来的断言都会当场跑。** `langcheck` 与 `layoutcheck` 是 macOS 可执行，编完立刻运行；
有模拟器时 `build.sh` 还会跑 `ordercheck` 和 `paracheck` 的三条端到端断言。**它们都会让构建
以非零码退出——它们是断言，不是演示。**

> 这一条是补出来的：在那之前 `langcheck` 与 `layoutcheck` **只被编译、从没被运行过**，
> 而本文档却写着「前两层是自动的」。于是一套全红的断言和一套全绿的产物在构建输出里长得
> 一模一样，「编译通过」被当成了「验过」——正是本仓库反复出问题的那一类谎。

## 工具

### `gen-image` — 生成中文测试图

渲染一张模拟药盒说明书的图：浅灰泛黄背景、深灰字（低对比度）、小字号、轻微模糊加噪。
刻意做成"手持拍摄"的样子，用来测苛刻条件下的识别质量。

```sh
./bin/gen-image /tmp              # 单栏说明书 → test_image.png
./bin/gen-image /tmp wrapped      # 一段话折五行 → test_image_wrapped.png
./bin/gen-image /tmp two-column   # 通栏题头 + 左右两栏 → test_image_two_column.png
./bin/gen-image /tmp column-tie   # 两栏同基线（人工参照）→ test_image_column_tie.png
```

第二个参数选版式，默认 `single`。同时会打印 `.accurate` 与 `.fast` 两档各自支持的语言清单。

四种版式都是夹具，各自钉一个方向：

| 版式 | 内容 | 用来 |
|---|---|---|
| `single` | 5 个小标题 + 每节一行正文 | `paracheck`：**该断的段要断开**（期望 10 段） |
| `wrapped` | 一段话折五行，无小标题 | `paracheck`：**折行的句子不能被拆散**（期望 1 段） |
| `two-column` | **通栏题头 + 左右各一栏正文** | `paracheck`：**分栏要切对**（期望 3 段：题头、左栏、右栏） |
| `column-tie` | 两个标题画在**同一条基线**上 | 人工用 `./bin/ocr` 看真实 `origin.y` 会不会完全相等 |

> **`two-column` 与 `column-tie` 别混，它们不是一回事。** `column-tie` 只有两个标题、
> 每栏一行，**它根本不是两栏版式**——那是给 `ordercheck` 的平局分支当人工参照用的
> （`ordercheck` 自己不读它，断言喂的是同几何的合成坐标）。
>
> 上面这张 `two-column` 是**补出来的**：原先那个名字挂着的是 `column-tie`，于是
> 「分栏在真图上到底成不成立」这一环**从来没有被量过**。真机报回来的正是它——
> 两栏正文左右跳。**一个名字指着一张测不了那件事的图，就是一层没人发现是空的覆盖。**

**行距是「下一行的字号」决定的，不是当前行的。** 这里原先写的是 `y -= size * 2.6`
（当前行），方向是反的：两行基线的距离由下一行的 space-before + leading 决定，标题上方
那段空白属于标题自己。用当前行的字号，大空白就落到了标题**之后**——`paracheck` 的段落
重建正是靠行距分布判段的，于是它会输出「正文和小标题粘在一起」，看着像代码坏了，其实是图不对。

### `ocr` — 对任意图片跑 OCR

```sh
./bin/ocr photo1.jpg photo2.jpg
```

按纵向位置排序输出文本块，附置信度和在画面中的高度百分比。用来测真实照片。

### `compare` — 对比语言配置

```sh
./bin/compare photo.jpg
```

同一张图跑 5 种语言/校正配置，并排输出，用来确认哪种配置对当前素材最好。

### `cold` — 冷启动计时

```sh
./bin/cold photo.jpg zh-Hans
```

测量某个语言首次使用的耗时（含模型准备）。**每次要用全新进程测**，否则测的是缓存。

已知行为：首次约 28–34s，之后 0.1–0.35s；按语言分别准备。

### `langcheck` — 断言识别语言规则

```sh
./bin/langcheck
```

不需要图片。它把 `RecognitionLanguage.swift` 与 `RecognitionLanguageAudit.swift` 的生产代码
原文件直接编进来（见 `build.sh`），共 176 条断言，覆盖八组规则。**「本机 Vision 支持清单」
以参数注入**，用的是真机实测的 33 种那份固定清单，所以这套断言不依赖跑它的机器。

1. **设备语言 → Vision 码 `systemLanguageCode`**：`de-AT` → `de-DE`、裸 `ja` → `ja-JP`、
   大小写不敏感；中文/粤语**按文字分档**——**显式的 `-Hans`/`-Hant` 子标签压过地区**
   （`zh-Hans-HK` / `zh-Hans-MO` / `zh-Hans-TW` 都是简体，`zh-Hant-CN` / `zh-Hant-MY` 都是
   繁体），只有没写文字时才拿地区推断（`zh-TW`/`zh-HK`/`zh-MO` 判繁体）；把清单倒序结果
   不变（证明分档不靠 `hasPrefix` 撞对）；设备清单里没有繁体时落简体；设备语言 Vision
   不认识（冰岛语）落英文，而不是递一个不存在的码
   > `zh-Hans-HK` / `zh-Hans-MO` 这几条是**补一个真出过的缺陷**：`Locale.availableIdentifiers`
   > 里确实有 `zh_Hans_HK` / `zh_Hans_MO`，iOS 上用户选「中文（简体）」加香港或澳门地区给的
   > 就是它们，而只看地区的实现会把它们判成繁体。补之前那 142 条里没有这两条，所以那个缺陷
   > 是**全绿通过**的——这也说明这套断言只覆盖它想到的情况。
2. **`visionLanguages`**：跟随系统取设备那一档；手动档与设备语言**完全无关**
   （德语设备 + 手动中文 → `zh-Hans`）；手动码本机不支持时落 `["en-US"]`
3. **`effectiveLanguageCode` 与 `visionLanguages` 一致**：两者分家的话，设置页的 ❗
   和阅读页的提示会描述一件实际没发生的事
4. **旧存储值迁移 `stored(from:supported:)`**：`chinese`/`english`/`german`… 那批档位名
   映射到码，`system`/`followApp` 都映射到 `.followSystem`；来路不明的码（`is-IS`）返回 nil。
   另含一条「旧档位名不查 `supported`」——它固定给出自己的码，能不能用由使用那一刻兜底
5. **往返**：33 个码逐个存得下、读得回、且真的喂给 Vision
6. **选项名 `displayName(for:)`**：5 个手工覆盖断言字面值；其余靠 `Locale` 生成，
   只断言性质（无空名、两两不撞名）——**不断言字面值**，那取决于系统 locale 数据，
   写死会让测试换台机器就假报错
7. **回归**：10 个中文/粤语设备语言都不许把 `en-US` 放首位（英文模型遇汉字静默输出垃圾，
   实测 `用法用量` → `mzms`）；德语设备不再拿到英文（改动前的默认档就是那样）
8. **`RecognitionLanguageAudit`**：只测**纯逻辑**那一层 `verdict`，假设以参数喂进来——
   不测 `audit`，它会去问 `NLLanguageRecognizer`，那是机器上的模型，写进断言等于让测试
   依赖环境（与第 6 组只断言性质同一个理由）。覆盖：语言码比较（含 `zh-Hans` / `zh-Hant`
   必须判为不同门、一边没写文字则不追究）、**实测的八种情况**、文字子标签那一档、
   「不重复建议正在用的那一档」、置信度门槛两侧与等号、边界（空递交 / 空假设）、
   以及两条**字数门槛**断言——它们在问模型**之前**就返回，所以无论这台机器上的模型怎么判
   都是 nil，可以放心断言字面值。
   > 第 8 组抓到的第一个缺陷是它自己的：断言原本写着「判成波兰语，但清单里没有所以不提示」，
   > 而 `pl-PL` **就在**那 33 条里——真按那样发布，App 会建议中文用户去改用波兰语。
   > 现在靠 `minimumSuggestionConfidence` 挡，那一组的注释里写明了这件事。

全部通过时退出码为 0。

### `layoutcheck` — 断言版式重建（视觉行 → 段落）

```sh
./bin/layoutcheck
```

不需要图片，也不需要 Vision。它把 `TextLayout.swift` 的生产代码原文件直接编进来，
共 34 条断言，全部喂**手造的 `TextLine` 几何**。

**这就是它不读图的原因。** 这一层的输入本来就是几何，断言就该直接喂几何——每条期望值是从
图形上读出来的，不是从某台机器某次识别的输出里抄来的，所以换台机器、换个系统版本结果不变。
真实照片那一环在 `paracheck`（见下），两者是分开的，别混着看。

四组：

1. **分块**（分栏 + 通栏行）：单栏 / 双栏 / 三栏；两栏**错开半行**时不交错（旧的按 `origin.y`
   兜底比较器在这里会逐行交错）；栏内按**基线**排序（同一行字大小不一时，上边缘会跟着字号
   跑偏），平局按 `minX` 升序；块的阅读顺序比较器是**全序**——两栏并排起头时上边缘相等，
   只比上边缘就会踩上 `sorted(by:)` 不稳定的那一脚。
   > **这里原来有一条断言把缺陷钉成了正确行为。** 它写着「有通栏行跨过竖缝时退回单栏」——
   > 而通栏行（居中题头）恰恰是真实说明书**到处都有**的东西，退化单栏之后按基线排就是
   > 真机报回来的**左右跳**。断言和代码一起错，于是全绿。现在那条改成「题头**自成一块**、
   > 排在两栏之前」，并补了 `centeredHeadingPage`（缺陷的原形）与 `strayLine`（参差右边界
   > 造的**假空档**：没有平衡判据就会把「一行 vs 其余所有行」当成两栏）。
2. **成段**：折行接成一段（中文不加空格、拉丁加空格、连字符断词去掉连字符）；段间距偏大 /
   段首缩进 / 上一行短且下一行齐头 → 断开；**满行 → 小标题 → 满行**在行距紧和行距松两种版式下
   结果必须一样。
   > 最后这条是 `paracheck` 端到端跑出来的。原先的判据算的是
   > `normalGap + max(normalGap * 0.8, height * 0.35)`——**基准取错了**：`normalGap` 是行间
   > 已有的空白，随行距设置漂（1.0 倍行距时趋近 0，2.0 倍时约一个行高），拿它当基数会让
   > 阈值的松紧跟着行距走，而且方向是反的。改成以**行高**为基准。
   > 两条断言是同一条不变量的两面：只钉一边，把系数往另一边调都「通过」。
3. **接行**：分隔符表（中文↔中文 / 拉丁↔拉丁 / 中英之间 / 连字符断词 / `Well-Being` 这类
   真连字符要留住）+ 完整接续。
4. **边界**：空输入、单行、只有两行时**判不出段落**（钉成已知局限：段间距的门槛建立在
   「本页相邻行距的中位数」上，两行只有一个间距样本，中位数就是它本身，间距信号恒不成立）。

> **夹具本身出过三次错，都记在这里。一处错得最贵——它不在这个文件里，是一个名字挂错了图。**
> 一处是 `isCJK` 漏了中文标点区（`，`U+FF0C、`。`U+3002 都不算 CJK），于是接缝落在句号上时就
> 凭空插一个空格——中文正文每在句子边界处折一次行就中一次。
> 另一处是「段首缩进」的夹具**图形自相矛盾**：正文 13 字占 0.80，字宽约 0.062，缩进两个字
> 该是 0.123，夹具却只给了 0.05。拿真版式里不存在的图形去问代码要答案，失败的是夹具不是代码。
>
> 第三次不在这一层：`gen-image` 里叫 `two-column` 的那张图**根本不是两栏版式**（只有两个标题、
> 每栏一行，是给 `ordercheck` 的平局分支当人工参照的）。名字听着像覆盖了分栏，实际什么都没
> 覆盖——于是分栏这一环**一直是空的**，直到真机上两栏正文左右跳才被发现。补的是 `gen-image`
> 里真正的两栏页 + 上面那条 `crossing` 断言。**名字比代码更能骗人：一个名字指着一张测不了
> 那件事的图，看不出任何异样，因为它不报错。**

全部通过时退出码为 0。

### `paracheck` — 端到端：真图片 → Vision → 段落

```sh
./bin/paracheck bin/test_image.png                 # 只打印
./bin/paracheck --expect 10 bin/test_image.png     # 段数对不上则退非零
./bin/paracheck bin/photo.jpg en-US                # 换语言（默认 zh-Hans en-US）
```

**它补的是 `ordercheck` 与 `layoutcheck` 之间那条缝。** 那两条的输入都是手造数据——一个喂合成
的 `VNRecognizedTextObservation`，一个喂手造的 `TextLine`。**两头都绿推不出「真照片进去、
成段的文字出来」**：中间那一段（Vision 在真实图像上给出的包围盒究竟多高、行距多大）谁都没量过，
而这一段恰恰是这个项目返工过两轮的地方——上一轮那套置信度阈值就是在合成图上标的。

它读一张图，全程走**生产代码**（`TextRecognitionService.blocks` → 坐标翻转 → `TextLayout.paragraphs`），
把视觉行几何、重建出的段落、以及**本页自己的统计量**（`normalGap` / `characterWidth` /
`typicalRightEdge`）一起打出来。判据全是相对的，所以这三个数就是这套判据在这张图上的全部依据——
真机行为不对时先看它们是不是离谱。

`build.sh` 每次跑三张图，缺一张这一环就不成立：

| 图 | 期望 | 钉的是 |
|---|---|---|
| `test_image.png` | **10 段** | 该断的没断（小标题被粘进上一段） |
| `test_image_wrapped.png` | **1 段** | 不该断的断了（折行的句子被拆散） |
| `test_image_two_column.png` | **3 段** | 分栏切错（题头 + 左右两栏；题头必须在两栏**之前**） |

**三个方向必须一起测。** 前两张是一对：只跑一张，把阈值往另一边调都「通过」——单看一张图是
看不出方向的。第三张钉的是另一个轴：间距判据再准，**块的顺序错了照样是一页读不通的文字**，
而它恰恰是真机唯一报回来的那条。

> 第三张是**补出来的**（见「`gen-image`」那节：`two-column` 这个名字原先挂的是另一张图）。
> 它说明的是这一层的覆盖面**是「轴」而不是「图」**：再加一张单栏图，加宽不了任何东西——
> 前两张已经把「间距判据的两个方向」占满了；换到「块的顺序」这个轴才加宽。**一个端到端
> 套件里全是同轴夹具，看上去很厚，其实只有一张。**

`paracheck` 的统计量是**按块**打的，不是拿整页所有行一起算。分栏之后同一条基线上并排的两行
间距算出来是**负的**，整页一起算会打出一个负的「正常行距」——那看着像代码坏了，其实是诊断
算错了范围，而它恰恰是出问题时第一个要看的数。

和 `ordercheck` 同因，它也是 iOS 模拟器产物（`OCRImageSource` 依赖 UIKit），必须经
`simctl spawn`，不能直接跑。

**输出 0 个视觉块不代表代码坏了**：那多半是这台模拟器上没有可用的识别模型。这种情况下这一环
什么都没验到，不能当成通过——`build.sh` 会把这句话明写出来，不让人从「跑完了」误读成「验过了」。

### `ordercheck` — 断言文本块阅读顺序

```sh
./bin/ordercheck
```

不需要图片，也不需要 OCR。它把 `TextRecognitionService.blocks(from:)` 这个生产比较器
原文件直接编进来，断言：同一基线上（`origin.y` 相等）的两个块按 `minX` 升序——**左栏在前**；
把输入顺序倒过来结果不变；主序（画面自上而下）不被平局分支盖掉；同一输入重排 200 次结果一致。

它必须编成 iOS 模拟器目标（比较器的输入类型是 `VNRecognizedTextObservation`），所以跑不了
就不能直接执行——见 `build.sh` 里那套按 UDID `simctl spawn` 的逻辑。
`RecognitionLanguage.swift` 也在它的编译清单里：`TextRecognitionService` 的语言码目录
（`OCRSupportedLanguageCodes.sorted`）要调 `displayName(for:)`，少了这个文件整个编译不过。

为什么不能像别的工具一样编成 macOS 可执行：比较器的输入类型是 `VNRecognizedTextObservation`，
只有 iOS SDK 有。所以 `build.sh` 把它编成 `arm64-apple-ios16.0-simulator`，
用 `xcrun simctl spawn <已启动的 iOS 模拟器 UDID> ./bin/ordercheck` 跑。它是**模拟器产物，
不能在 shell 里直接执行**（会报 `DYLD_ROOT_PATH not set for simulator program`）。
UDID 由 `build.sh` 按运行时分组自己挑，**只认 iOS**——`simctl spawn booted` 会把 watchOS /
tvOS / visionOS 的设备一起列为候选，挑错了就是一次假失败（编出来的东西跑不起来）。
没有可用的 iOS 模拟器时 `build.sh` 会明确跳过并说明原因，不算构建失败。

平局分支对应的测试图是 `gen-image` 的 `column-tie` 版式，**但 ordercheck 不读它**：上面几条
断言喂的是与那张图几何一致的合成坐标（左栏 x=0.05、右栏 x=0.55），不碰像素、不碰 Vision——
这正是它能离线跑的原因。图是给**人工**验的：

```sh
./bin/gen-image /tmp column-tie   # 写出 /tmp/test_image_column_tie.png
./bin/ocr /tmp/test_image_column_tie.png   # 看真实 Vision 给两个标题各报什么 origin.y
```

两个栏目标题画在同一条基线上，正是平局分支要处理的形状。

> 这张图**曾经叫 `two-column`**，后来那个名字给了一张真正的两栏页（通栏题头 + 左右两栏），
> 它才改名成 `column-tie`。改名不是洁癖：旧名字会让人以为分栏已经被覆盖过了，而它其实一行
> 正文都没有。见「`gen-image`」那节的框。ordercheck 断言的是「**若**两个块
`origin.y` 相等，则左栏在前」这条规则；真实 Vision 是否真会给出完全相等的 `origin.y`，本仓库
没有测过（也不需要——规则本身跟谁产生这些块无关）。

## 用途：回归测试

`compare` 的固定配置输出可直接用于断言。建议固化的两条：

1. 中文图 + `["zh-Hans"]` → 识别率达标
2. **中文图 + `["en-US"]` → 必须失败**

第 2 条是把已知陷阱钉死，防止将来有人「优化」语言列表顺序时静默搞坏。

段落重建（`TextLayout`）的回归靠三层，**缺一层就有一种错法能溜过去**：

| 层 | 工具 | 能挡住的 |
|---|---|---|
| 纯几何 | `layoutcheck` | 分栏切错、排序错、该接的行断开——输入是手造几何，最稳也最窄 |
| 端到端 | `paracheck` | 坐标翻转反了、真实包围盒下判据不成立——**两个方向都要跑** |
| 真机 | 用户手上的设备 | 合成图里没有的东西：透视、光照、反光、真实版式 |

前两层是自动的（`build.sh` 跑）。第三层不能替——`paracheck` 读的是合成图，
它的行距和字宽都太规整，**证明不了阈值在真实照片上够用**。

> **「缺一层就有一种错法能溜过去」不是推测，是量出来的。** 把 `heightFactor` 从 0.35 改成
> 0.95（一个足以把说明书图从 10 段打成 6 段的破坏）再跑 `build.sh`：**`layoutcheck` 全部通过**
> ——它的「行距松」那条夹具算出来是阈值 0.049、实际间距 0.05，**以 2% 的余量勉强躲过去了**；
> `paracheck` 当场报「段数 6，期望 10」。两层的分工就是这么具体：手造几何那层只能钉住它自己
> 写下来的那组数，真图那层才能发现「这组数离真实版式有多近」。
> （那次实验还顺带查出 `build.sh` 的两个缺陷，见「构建」一节。）
>
> 反过来也有一次，而且更值得记：**分栏那个缺陷是 `layoutcheck` 放过去的**——不只是没测到，
> 是**测到了并断言成正确行为**（见上面第 1 组那个框）。一层全覆盖的绿，可能来自它只覆盖了
> 代码**做对了**的那些形状。

## 局限

- 跑在 macOS 上。Vision 在 iOS 和 macOS 是同一套 API，**但结果不保证逐字相同**，
  设备端仍应复验。
- `gen-image` 产出的是合成图，不含真实照片的透视畸变、光照不均、反光、复杂版式。
  真实素材请用 `ocr` / `compare` / `paracheck` 直接喂照片。
- **`TextLayout` 的判据阈值没有在真实照片上标定过。** `heightFactor` 是在一张合成图上定的
  （`paracheck` 的说明书图，实测段间距超出量约 0.61 个行高）。`paracheck` 能把本页统计量
  打出来，真机跑一遍再决定要不要动这个数——**别照着合成图调**。本项目上一轮的置信度阈值就是
  在合成图上标的，真机行为与标定不符，返工了两轮。
- 段落重建只能还原**本页内部自洽**的结构。版式本身就怪（无行距差、无缩进、无短行的均匀密排）
  时它没有办法，也不该硬猜——那种情况本来就没有可用的信号。
- 无法区分「首次 28s 是网络下载还是本地编译」——两者都会写文件缓存。
  需真机断网实测。
