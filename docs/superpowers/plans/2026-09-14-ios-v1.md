# PresbyFriend iOS v1 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 iOS 版从「有骨架但链路不通」补到与 Android 能力对齐：三个入口（剪贴板、分享、拍照/选图）都能把内容送进同一套阅读模式并可朗读。

**Architecture:** 图片一律走 `Vision` OCR 转文本，再与文本/URL 合流进现有的 `ReaderView`。三个入口不各写一套跳转逻辑，而是共用 `ReaderLaunchCoordinator`。放大镜本身保持纯数字放大，不内嵌 OCR。

**Tech Stack:** Swift 5 / SwiftUI / Vision（`VNRecognizeTextRequest`）/ PhotosUI / VisionKit / AVFoundation。部署目标 iOS 16.0。

## Global Constraints

- 部署目标 `IPHONEOS_DEPLOYMENT_TARGET = 16.0`。**不得使用 iOS 17+ API**，特别是两参数形式的 `onChange(of:initial:_:)`。
- OCR 必须用 `recognitionLevel = .accurate`。`.fast` 档不支持中文（只有 en/fr/it/de/es/pt），对中文图返回 0 结果。
- `recognitionLanguages` 的**第一个元素决定用哪个识别模型**。中文场景必须把 `zh-Hans` 放在第一位；英文模型遇汉字会静默输出垃圾（不报错、不崩溃）。
- 所有 UI 字符串经 `L10n` 引用，且必须**同时**写进 `en/de/fr/es/it/pt` 六个 `Localizable.strings`。六份文件的 key 集合必须完全一致。
- 不得改动 `android/` 下任何文件。
- 根目录 `PresbyFriend/`、`Shared/`、`ShareExtension/` 保留不动（已确认构建不依赖，清理需单独确认）。
- 工程用 `PBXFileSystemSynchronizedRootGroup`：新增 `.swift` 文件自动被收录，**不要**改 `project.pbxproj` 去加文件引用。`shareextention` target 同时收录了 `PresbyFriend` 组，所以新增文件会同时进两个 target——因此新代码里不能出现扩展中不可用的 API（如 `UIApplication.shared`）。

**工作目录约定：** 所有 `xcodebuild` 命令在 `/Users/mac/laohuazhiyou/ios/PresbyFriend` 下执行。git 命令在 `/Users/mac/laohuazhiyou` 下执行。当前分支 `ios-v1`。

## Task 3: 识别语言选择 + 回归测试

**Files:**
- Create: `ios/PresbyFriend/PresbyFriend/Core/OCR/RecognitionLanguage.swift`
- Create: `tools/ocr-bench/langcheck.swift`
- Modify: `tools/ocr-bench/build.sh`

**Interfaces:**
- Consumes: 无
- Produces:
  - `enum RecognitionLanguage: String, CaseIterable, Identifiable`，cases 为 `.system` / `.chinese` / `.english`
  - `static func visionLanguages(systemLanguageCode: String?, preference: RecognitionLanguage) -> [String]`

> **事后更正（2026-09-16）：上面的三档 `.system` / `.chinese` / `.english` 与
> `visionLanguages(systemLanguageCode:preference:)` 已被推翻**，改成九档 + 两个纯函数。
> 推翻的理由是一个真实缺陷，不是偏好：
>
> 旧的 `.system` 实现只有两档——`code.hasPrefix("zh") ? ["zh-Hans"] : ["en-US"]`。也就是
> 说德语用户的「跟随系统」真实含义是**英语**，而 `ocr_language_desc` 自己正写着「选错会让
> 识别静默失败」。而 Vision 从 revision 2（iOS 14）起就同时支持
> `en-US fr-FR it-IT de-DE es-ES pt-BR zh-Hans zh-Hant`——**恰好是六种 App 语言加中文**，
> 这些语言一直认得，只是选项集里没有它们（本机枚举 `supportedRecognitionLanguages` 实测）。
>
> 现在的形状：
> - cases：`.followApp` / `.english` / `.german` / `.french` / `.spanish` / `.italian` /
>   `.portuguese` / `.chineseSimplified` / `.chineseTraditional`；声明顺序即 `allCases`，
>   即设置页里的显示顺序
> - `visionLanguages(appLanguageCode:preference:)`——输入从**设备语言**改成**App 语言**
>   （`settings.language`）。`.followApp` 因此字面为真，且与设置页上方那个语言选择器自洽
> - `initialDefault(deviceLanguageCode:)`——**只在存储为空时**用一次。没有它，
>   `.followApp` 叠上 App 语言的默认值 `"en"` 会让**所有**新用户拿到英文，中文用户从此前的
>   「设备是中文就自动给中文」掉到「英文」，而中文本是这个 App 最主要的使用场景。那是一次
>   回退，必须堵住。其余设备语言一律给 `.followApp`，与改动前的实际行为一致
> - `storedValue(from:)`——迁移旧 rawValue `system` / `chinese` / `english`。不映射的话
>   `init(rawValue:)` 返回 nil 再被 `??` 兜成默认值，用户选过的「中文」会被**静默重置**

> **事后更正之五（2026-09-16）：上面那套「分栏 → 排序 → 成段」交付后，真机仍然「左右跳」。
> 分栏的判据取错了量。**
>
> 用户回报原文：**「真机现在还是左右跳」**。段是分出来了，但在两栏版面上**块的顺序**是错的——
> 左栏一行、右栏一行地交替，读出来还是词串；标题出现在两栏**之间**。
>
> **根因：判据要的是「并集里的零空档」，而真实页面里那条缝总被跨过。**
> 更正之四定的是「求所有行横向区间的**并集**，并集内部的空档就是候选栏缝」——这句话等价于
> 要求**没有任何一行**跨过这条缝。而真实说明书最常见的版式是**一条居中题头横跨栏缝**：它把
> 并集连成一片，于是**真正的栏缝一条都找不到**；反倒因为题头够不到左右两栏的边界，在题头旁边
> 裂出一条**窄缝**，被当成栏缝挑走。结果「左栏」自成一块、「右栏 + 题头」粘成另一块——
> **标题落到两栏中间**。
>
> **这不是「没测到」，是「测到了并把它断言成了正确行为」。** `layoutcheck` 当时**有一条**
> 断言写着「有通栏行跨过竖缝时退回单栏（不丢行）」——那正是缺陷的形状，被钉成了预期。
> 断言与代码一起错，于是全绿。**同时** `gen-image` 里叫 `two-column` 的夹具**根本不是两栏页**
> （只有两个标题、每栏一行，是给 `ordercheck` 的平局分支当人工参照用的），所以
> 「分栏在真图上到底成不成立」**从来没有被量过**。两层同时空着，缺陷一路走到用户手上。
> 教训一句话：**一个名字指着一张测不了那件事的图，看不出任何异样，因为它不报错。**
>
> **修法：候选从「并集的空档」改成「边界之间的区间」。** 把所有 `minX` / `maxX` 排序，相邻
> 两个值之间就是一个候选；有行跨过某条缝时那条缝**依然是一个候选区间**，只是「跨越行数」不为
> 零——两个量一起用来排名。三件事依次筛：够宽且**在页内**（左右留白不是栏缝）；跨越行数
> ≤ `columnCrossingFraction`（0.25，通栏行是少数，一两条正常）；两侧行数 ≥
> `columnBalanceFraction`（0.2，挡「一栏 + 一条短行」——参差的右边界会在栏内裂出假空档，
> 那种空档两侧是「一行 vs 其余所有行」）。**排名先比宽度，再比跨越行数**：顺序反了会挑走题头
> 旁那条窄缝，它跨越行数为 0、比真栏缝「更干净」，但**真栏缝总是更宽**。通栏行**各自成块**，
> 按块顺序排在两栏之前；块顺序比较器必须是**全序**（上边缘平局时比左边缘），因为两栏并排
> 起头时上边缘几乎总是相等，而 `sorted(by:)` 不保证稳定——`ordercheck` 存在的全部理由就是
> 不让人踩这一脚。
>
> **两层空着的覆盖一起补上：** `layoutcheck` 那条错误断言换成「题头自成一块、排在两栏之前」，
> 并新增 `centeredHeadingPage`（缺陷原形）与 `strayLine`（平衡判据）→ **32 条变 34 条**；
> `gen-image` 新增**真正的两栏页**（通栏题头 + 左右各一栏，旧的 `two-column` 改名
> `column-tie`）；`paracheck` 对它断言**恰好 3 段**，`build.sh` 每次跑**三张图**。
> `paracheck` 的统计量改为**按块**打印——整页一起算时并排两栏的行距是**负的**，而它恰恰是
> 出问题时第一个要看的数。
>
> **这一层的覆盖面是「轴」不是「图」**：更正之四那两条端到端断言都在同一个轴（间距判据的
> 松紧）上，再加一张单栏图加宽不了任何东西；「块的顺序」这个轴一条断言都没有，而它正是真机
> 唯一报回来的那条。
>
> **未验证 / 待真机**：两栏夹具是**合成图**。需用户在真机上重拍两栏材料复验；若仍不对，
> 要用户的**原始照片**——`paracheck <照片>` 可以直接喂它，用真实几何而不是再猜一张合成图。

**背景：** 这是整个 App 最危险的开关。`recognitionLanguages` 的第一个元素选中识别模型，选错则**不报错、不崩溃，只是安静输出垃圾**——历史上两次「OCR 乱七八糟」（PWA 用 Tesseract.js `chi_sim`、Android 早期用 Latin-only 识别器）都是这个成因。所以判断逻辑集中在这一个纯函数里，并且给它配一个能跑的回归测试。

**关于测试方式：** 本工程没有 XCTest target，且新增 target 需要手改 `project.pbxproj` 并另写 `.xcscheme`（自动生成的 scheme 只在 Xcode 打开工程时产生，命令行无法触发）。因此改用与 `tools/ocr-bench/` 一致的既有做法：把这个**纯 Foundation 文件**直接编进一个独立可执行文件做断言。这样测的是生产代码本身，且不需要动工程文件。

```swift
import Foundation

/// 识别语言偏好。三种取值，`system` 为默认。
///
/// 刻意只 `import Foundation`、不引用 `L10n` 或任何 UI 类型——这样它可以被
/// `tools/ocr-bench/langcheck` 单独编出来跑断言。显示用的文案在设置页里给。
enum RecognitionLanguage: String, CaseIterable, Identifiable {
    case system
    case chinese
    case english

    var id: String { rawValue }

    /// 构造 Vision 的 `recognitionLanguages`。
    ///
    /// **数组的第一个元素决定用哪个识别模型。** 选错不会报错、不会崩溃，只会
    /// 安静地输出垃圾（实测：中文图 + `["en-US"]` 把「用法用量」识别成 `mzms`）。
    /// 中文模型能勉强认拉丁字母，英文模型遇汉字直接崩，所以中文场景必须把
    /// `zh-Hans` 放在第一位。
    ///
    /// - Parameters:
    ///   - systemLanguageCode: 系统语言码，如 `"zh-Hans"`、`"de-DE"`。可为 nil。
    ///   - preference: 用户在设置页的选择；`.system` 表示跟随系统。
    static func visionLanguages(systemLanguageCode: String?,
                                preference: RecognitionLanguage) -> [String] {
        switch preference {
        case .chinese:
            return ["zh-Hans"]
        case .english:
            return ["en-US"]
        case .system:
            let code = systemLanguageCode?.lowercased() ?? ""
            return code.hasPrefix("zh") ? ["zh-Hans"] : ["en-US"]
        }
    }
}
```

**背景（方向问题，容易静默出错）：** `CGImageSourceCreateImageAtIndex` **不会**应用 EXIF 方向。后置摄像头的传感器是横向的，拍出来通常带方向元数据（`kCGImagePropertyOrientation`）。如果直接把未旋转的 `CGImage` 丢给 Vision，识别质量会下降甚至返回空——又是一次「不报错但结果不对」。所以方向必须在构造时就带上，并传给 `VNImageRequestHandler(cgImage:orientation:options:)`。

- [ ] **Step 1: 实现 `OCRImageSource.swift`**

```swift
import Foundation
import UIKit
import ImageIO
import CoreGraphics

/// 一张待识别的图，连同它的方向。
///
/// 三个来源（相册选图 / 分享附件 / 相机快门）都归一到这个类型，
/// 这样 `TextRecognitionService` 不需要知道图是从哪来的。
///
/// **为什么要带方向：** `CGImageSourceCreateImageAtIndex` 不会应用 EXIF 方向。
/// 手机摄像头传感器是横向的，照片通常带方向元数据。忽略它会让 Vision 拿到一张
/// 躺倒的图，识别质量下降甚至返回空——不报错，只是结果不对。
struct OCRImageSource {
    var image: CGImage
    var orientation: CGImagePropertyOrientation = .up

    /// 从图片二进制（相册选图、分享附件、`AVCapturePhoto.fileDataRepresentation()`）构造。
    static func from(data: Data) -> OCRImageSource? {
        guard let src = CGImageSourceCreateWithData(data as CFData, nil),
              let img = CGImageSourceCreateImageAtIndex(src, 0, nil) else { return nil }
        let props = CGImageSourceCopyPropertiesAtIndex(src, 0, nil) as? [CFString: Any]
        let raw = (props?[kCGImagePropertyOrientation] as? UInt32) ?? 1
        return OCRImageSource(image: img,
                              orientation: CGImagePropertyOrientation(rawValue: raw) ?? .up)
    }

    /// 从 `UIImage` 构造（部分分享扩展的 `NSItemProvider` 直接给 `UIImage`）。
    static func from(uiImage: UIImage) -> OCRImageSource? {
        guard let cg = uiImage.cgImage else { return nil }
        let orientation: CGImagePropertyOrientation
        switch uiImage.imageOrientation {
        case .up:            orientation = .up
        case .down:          orientation = .down
        case .left:          orientation = .left
        case .right:         orientation = .right
        case .upMirrored:    orientation = .upMirrored
        case .downMirrored:  orientation = .downMirrored
        case .leftMirrored:  orientation = .leftMirrored
        case .rightMirrored: orientation = .rightMirrored
        @unknown default:    orientation = .up
        }
        return OCRImageSource(image: cg, orientation: orientation)
    }
}
```

- [ ] **Step 2: 实现 `TextRecognitionService.swift`**

```swift
import Foundation
import Vision
import CoreGraphics

/// 一个识别出的文本块。
struct RecognizedBlock: Equatable {
    let text: String
    /// 0 = 画面顶部，1 = 画面底部。用于恢复阅读顺序。
    let topYRatio: Double
}

/// 唯一接触 Vision 的地方：把「一张图」变成「一串文本块」。
final class TextRecognitionService {

    /// 当前生效的识别语言。由调用方根据 `RecognitionLanguage.visionLanguages` 设置——
    /// 本服务不猜，猜错的代价是静默输出垃圾。
    var languages: [String]

    private let queue = DispatchQueue(label: "com.presbyfriend.ocr")

    init(languages: [String] = ["en-US"]) {
        self.languages = languages
    }

    func recognize(_ source: OCRImageSource) async throws -> [RecognizedBlock] {
        let languages = self.languages
        return try await withCheckedThrowingContinuation { continuation in
            queue.async {
                let request = VNRecognizeTextRequest()
                // 必须 .accurate：.fast 档不支持中文（只有 en/fr/it/de/es/pt），
                // 对中文图返回 0 个结果，没有「降档换速度」的余地。
                request.recognitionLevel = .accurate
                request.recognitionLanguages = languages
                request.usesLanguageCorrection = true

                let handler = VNImageRequestHandler(cgImage: source.image,
                                                    orientation: source.orientation,
                                                    options: [:])
                do {
                    try handler.perform([request])
                    continuation.resume(returning: Self.blocks(from: request.results ?? []))
                } catch {
                    continuation.resume(throwing: error)
                }
            }
        }
    }

    /// 启动时后台调用，避免用户第一次按快门要等模型准备。
    ///
    /// 实测：某个语言模型首次使用约 28–34s（一次性），之后 0.1–0.35s，按语言分别准备。
    /// 这里喂一张 8×8 的空白图——目的是触发模型加载，不指望识别出东西。
    /// 已知局限：这是尽力而为，失败静默吞掉；且「首次慢到底是网络下载还是本地编译」
    /// 尚未验证（见设计文档「已决事项 2」），若依赖网络则无网时会退化为按快门才等。
    func prewarm() async {
        let size = 8
        let cs = CGColorSpaceCreateDeviceRGB()
        guard let ctx = CGContext(data: nil, width: size, height: size,
                                  bitsPerComponent: 8, bytesPerRow: 0, space: cs,
                                  bitmapInfo: CGImageAlphaInfo.premultipliedLast.rawValue),
              let blank = ctx.makeImage() else { return }
        _ = try? await recognize(OCRImageSource(image: blank))
    }

    /// 按纵向位置排序（画面上方到下方），恢复阅读顺序。
    static func blocks(from observations: [VNRecognizedTextObservation]) -> [RecognizedBlock] {
        observations
            .sorted { $0.boundingBox.origin.y > $1.boundingBox.origin.y }
            .compactMap { obs in
                guard let top = obs.topCandidates(1).first else { return nil }
                let box = obs.boundingBox
                return RecognizedBlock(text: top.string,
                                       topYRatio: 1.0 - Double(box.origin.y + box.height))
            }
    }
}
```

```swift
import SwiftUI
import CoreGraphics
import Combine   // 必需：本工程开了 MEMBER_IMPORT_VISIBILITY，@Published 不会从 SwiftUI 透出来

/// 送进阅读模式的内容。
enum ReaderContent {
    case text(String)
    case image(OCRImageSource)
}

/// 承载「某段内容 → 打开阅读模式」这一个动作，三个入口共用。
@MainActor
final class ReaderLaunchCoordinator: ObservableObject {

    /// 是否展示阅读模式。
    @Published var isPresenting = false
    /// 正在 OCR。UI 用它显示「正在准备」而不是卡住。
    @Published var isPreparing = false
    /// 待阅读的文本。OCR 成功后由识别结果填入。
    @Published var text: String?
    /// OCR 没认出文字时的兜底：直接显示原图（只支持缩放）。
    @Published var fallbackImage: OCRImageSource?

    private let ocr = TextRecognitionService()

    /// 语言数组的构造在 `RecognitionLanguage` 里，这里只是转发给 OCR 服务。
    func updateLanguages(_ languages: [String]) {
        ocr.languages = languages
    }

    /// 启动时后台预热识别模型，避免用户第一次按快门要等很久。
    func prewarm() {
        let service = ocr
        Task.detached(priority: .utility) {
            await service.prewarm()
        }
    }

    func open(text: String) {
        let trimmed = text.trimmingCharacters(in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty else { return }
        fallbackImage = nil
        self.text = trimmed
        isPresenting = true
    }

    func open(image source: OCRImageSource) async {
        isPreparing = true
        defer { isPreparing = false }

        let blocks = (try? await ocr.recognize(source)) ?? []
        let joined = blocks.map(\.text).joined(separator: "\n")

        if joined.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty {
            // 空结果不算错误：兜底显示原图，让用户自己放大看。
            text = nil
            fallbackImage = source
        } else {
            text = joined
            fallbackImage = nil
        }
        isPresenting = true
    }

    func close() {
        isPresenting = false
        text = nil
        fallbackImage = nil
    }
}
```

- [ ] **Step 2: 实现 `ZoomableImageView.swift`**

```swift
import SwiftUI
import UIKit

/// OCR 没认出文字时的兜底：显示原图，支持捏合缩放和拖动。
///
/// 用 `UIScrollView` 而不是 SwiftUI 的 `MagnificationGesture`——前者直接给出
/// 平滑的捏合 + 平移 + 回弹，不用自己维护缩放锚点和边界。
struct ZoomableImageView: UIViewRepresentable {
    let image: UIImage
    /// 最小缩放。默认 1 表示「适应屏幕」，用户可以往外捏。
    var minimumZoomScale: CGFloat = 1.0
    var maximumZoomScale: CGFloat = 8.0

    func makeUIView(context: Context) -> UIScrollView {
        let scrollView = UIScrollView()
        scrollView.delegate = context.coordinator
        scrollView.minimumZoomScale = minimumZoomScale
        scrollView.maximumZoomScale = maximumZoomScale
        scrollView.bouncesZoom = true
        scrollView.showsHorizontalScrollIndicator = false
        scrollView.showsVerticalScrollIndicator = false
        scrollView.backgroundColor = .black

        let imageView = UIImageView(image: image)
        imageView.contentMode = .scaleAspectFit
        imageView.isUserInteractionEnabled = true
        scrollView.addSubview(imageView)
        context.coordinator.imageView = imageView

        // 双击放大到 2 倍 / 还原。比拇指捏合更容易被老花眼用户发现。
        let doubleTap = UITapGestureRecognizer(
            target: context.coordinator,
            action: #selector(Coordinator.handleDoubleTap(_:)))
        doubleTap.numberOfTapsRequired = 2
        scrollView.addGestureRecognizer(doubleTap)

        return scrollView
    }

    func updateUIView(_ scrollView: UIScrollView, context: Context) {
        context.coordinator.imageView?.image = image
        context.coordinator.layout(in: scrollView)
    }

    func makeCoordinator() -> Coordinator { Coordinator() }

    final class Coordinator: NSObject, UIScrollViewDelegate {
        var imageView: UIImageView?

        func layout(in scrollView: UIScrollView) {
            guard let imageView else { return }
            scrollView.frame = scrollView.bounds
            imageView.frame = scrollView.bounds
            scrollView.contentSize = scrollView.bounds.size
        }

        func viewForZooming(in scrollView: UIScrollView) -> UIView? { imageView }

        func scrollViewDidZoom(_ scrollView: UIScrollView) {
            guard let imageView else { return }
            let offsetX = max((scrollView.bounds.width - imageView.frame.width) / 2, 0)
            let offsetY = max((scrollView.bounds.height - imageView.frame.height) / 2, 0)
            scrollView.contentInset = UIEdgeInsets(top: offsetY, left: offsetX,
                                                   bottom: offsetY, right: offsetX)
        }

        @objc func handleDoubleTap(_ recognizer: UITapGestureRecognizer) {
            guard let scrollView = recognizer.view as? UIScrollView else { return }
            if scrollView.zoomScale > scrollView.minimumZoomScale {
                scrollView.setZoomScale(scrollView.minimumZoomScale, animated: true)
            } else {
                let point = recognizer.location(in: imageView)
                let target = min(scrollView.maximumZoomScale, scrollView.minimumZoomScale * 2.5)
                let width = scrollView.bounds.width / target
                let height = scrollView.bounds.height / target
                scrollView.zoom(
                    to: CGRect(x: point.x - width / 2, y: point.y - height / 2,
                               width: width, height: height),
                    animated: true)
            }
        }
    }
}
```

## Task 6: 三个 tab + 读取页（粘贴入口）+ 删除自动读剪贴板

**Files:**

**Interfaces:**

**修的 bug：** `PresbyFriendApp.swift` 现在在 `.onAppear` 和每次回到前台都调 `checkClipboard()`，里面直接读 `UIPasteboard.general.string`。iOS 16 起这会弹系统对话框（「PresbyFriend」想要粘贴自「微信」/ 不允许 · 允许粘贴），**每次回前台都弹**。危害恰好命中核心场景——老人用这个 App 主要就是从别的 app 复制内容。

**已查证的两条事实（决定方案）：**

1. 普通按钮里读 `UIPasteboard.general.string`，**每次点击都弹**，不是只弹一次。Apple 只对系统识别的粘贴手势（`UIPasteControl`、`UIAction.Identifier.paste` 菜单、⌘V）免弹窗。
2. `UIPasteControl.Configuration` 只暴露 `displayMode` / `cornerStyle` / `cornerRadius` / `baseBackgroundColor` / `baseForegroundColor`，**没有字号入口**。

所以两个选项的真实代价是：普通大字按钮（字体可做大，但每次弹窗）对 `UIPasteControl`（永不弹窗，但标签字号固定约 17pt）。**选 `UIPasteControl`**——对这个人群，每次粘贴都被系统对话框打断，比按钮标签字号小更难受。点击区域靠 `frame` 做大，大字说明放在卡片标题位（自有文字，字号随意）。

**另一个必须处理的点：** `UIPasteControl` 在剪贴板为空时是禁用状态。我们**不读** `UIPasteboard` 去检测是否为空（会引入新的弹窗风险），改为在按钮下方常驻一句提示文案。

- [ ] **Step 1: 实现 `PasteControlView.swift`**

```swift
import SwiftUI
import UIKit
import UniformTypeIdentifiers

/// `UIPasteControl` 的 SwiftUI 包装。
///
/// 为什么不用普通 Button + `UIPasteboard.general.string`：那样**每次点击**都会弹
/// 系统对话框，且无法用 API 查询用户的选择。`UIPasteControl` 是 Apple 认可的
/// 「用户意图」信号，永不弹窗。
///
/// 代价是标签字号不可调（`UIPasteControl.Configuration` 没有字号属性），
/// 所以调用方应把大字说明放在控件之外。
struct PasteControlView: UIViewRepresentable {
    /// 拿到粘贴的纯文本后回调（主线程）。
    let onPaste: (String) -> Void

    func makeUIView(context: Context) -> UIPasteControl {
        let config = UIPasteControl.Configuration()
        config.displayMode = .iconAndLabel
        config.cornerStyle = .capsule
        config.baseBackgroundColor = .systemBlue
        config.baseForegroundColor = .white

        let control = UIPasteControl(configuration: config)
        control.target = context.coordinator
        return control
    }

    func updateUIView(_ uiView: UIPasteControl, context: Context) {
        context.coordinator.onPaste = onPaste
    }

    func makeCoordinator() -> Coordinator { Coordinator(onPaste: onPaste) }

    /// `UIPasteControl` 的 target 需要是 `UIResponder` 并声明可接受的类型。
    final class Coordinator: UIResponder {
        var onPaste: (String) -> Void

        init(onPaste: @escaping (String) -> Void) {
            self.onPaste = onPaste
            super.init()
            pasteConfiguration = UIPasteConfiguration(
                acceptableTypeIdentifiers: [UTType.plainText.identifier])
        }

        override func canPaste(_ itemProviders: [NSItemProvider]) -> Bool {
            itemProviders.contains { $0.hasItemConformingToTypeIdentifier(UTType.plainText.identifier) }
        }

        override func paste(itemProviders: [NSItemProvider]) {
            for provider in itemProviders
            where provider.hasItemConformingToTypeIdentifier(UTType.plainText.identifier) {
                provider.loadItem(forTypeIdentifier: UTType.plainText.identifier) { item, _ in
                    let text = (item as? String)
                        ?? (item as? Data).flatMap { String(data: $0, encoding: .utf8) }
                    guard let text, !text.isEmpty else { return }
                    DispatchQueue.main.async { self.onPaste(text) }
                }
                return
            }
        }
    }
}
```

```swift
/// 「读取」tab：老花眼用户最高频的动作，值得一整屏、值得把按钮做大。
```

```swift
    /// 从附件里取第一张可用的图。
    /// 三种形态都要兜：Data、临时文件 URL、以及同进程传过来的 UIImage。
    private func extractImage(from attachments: [NSItemProvider]) async -> OCRImageSource? {
        for provider in attachments
        where provider.hasItemConformingToTypeIdentifier(UTType.image.identifier) {
            if let data = try? await provider.loadItem(forTypeIdentifier: UTType.image.identifier) as? Data,
               let source = OCRImageSource.from(data: data) {
                return source
            }
            if let url = try? await provider.loadItem(forTypeIdentifier: UTType.image.identifier) as? URL,
               let data = try? Data(contentsOf: url),
               let source = OCRImageSource.from(data: data) {
                return source
            }
            if let image = try? await provider.loadItem(forTypeIdentifier: UTType.image.identifier) as? UIImage,
               let source = OCRImageSource.from(uiImage: image) {
                return source
            }
        }
        return nil
    }

    private func loadImage(_ source: OCRImageSource) async {
        let service = TextRecognitionService(
            languages: RecognitionLanguage.visionLanguages(
                systemLanguageCode: Locale.current.language.languageCode?.identifier,
                preference: settings.recognitionLanguage))
        let blocks = (try? await service.recognize(source)) ?? []
        let joined = blocks.map(\.text).joined(separator: "\n")
        if joined.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty {
            error = L10n.ocrNoText
        } else {
            text = joined
        }
    }
```

### 1. 最贵的一件事：`Locale.current` 不是用户的系统语言

**机制**：`Locale.current` 是**按本 App 的本地化过滤之后**的结果，不是用户的系统语言。
本 App 只出六种语言（`ios/PresbyFriend/PresbyFriend/` 下只有 en/de/fr/es/it/pt 六个 `.lproj`，
`developmentRegion = en`，没有 `CFBundleLocalizations`；`find ios -iname '*zh*'` **为 0**），
所以在**中文设备**上它返回 `"en"`。而 `RecognitionLanguage.visionLanguages` 的 `.system` 分支是
`code.hasPrefix("zh") ? ["zh-Hans"] : ["en-US"]`，而 `.system` 正是**默认值**——于是最主流的路径
（中文设备 + 默认设置 + 拍一张中文）默认跑英文模型。

**两次独立实测**：

1. 终审用同形状的探针包在 booted 模拟器上测得 `Locale.current.identifier = en_CN` /
   `languageCode = en` / `preferredLanguages[0] = "zh-Hans-CN"`。
2. 实施方在**模拟器上真装好的本 App** 里用 `-AppleLanguages (zh-Hans)` 注入探针复核，结果一致。

**后果用本仓库自己的工具、在自己的 fixture 上量到**：`en-US` only → **4 块**，内容是 `mzms`；
`zh-Hans` only → **10 块**，`用法用量` / `不良反应` 全部正确。**不报错、不崩溃。**

这一条的严重性在于它是全分支**唯一一处「错了也不告诉你」**的缺陷：其他缺陷都以某种方式露出来
（崩溃、空屏、英文串），只有它安静地输出垃圾——而它偏偏落在最主流的路径上。

**处置**：代码改用 `Locale.preferredLanguages.first`（commit `e116886`）；**计划文本本身也写错了**
（Task 6 与 Task 9 的代码块、设计文档对应处都写的是 `Locale.current`），已同步更正。
`RecognitionLanguage.visionLanguages` 那个纯函数是**对的**，它的测试预期一条都不该改——错的只是
喂给它的值。非中文系统下两个 API 结果相同，所以这一改**只影响中文**。

> **⚠️ `-AppleLanguages` 不能用来切本 App 的界面语言**（2026-09-15 收尾实测纠正；原先这里写的是

> `Core/i18n/LanguageManager.swift:38` 用 `object_setClass(Bundle.main, LanguageAwareBundle.self)`
> 把 `Bundle.main` 换掉，`LanguageAwareBundle.localizedString`（`:25-32`）只按
> **`LanguageManager.shared.current`** 去取 `.lproj`，**根本不看系统语言**；而 `current` 在启动时
> 被 `PresbyFriendApp.swift:41` 从 `settings.language` 覆盖一次——那是 **App Group
> `group.com.presbyfriend` 里的 `language` 键**（`Shared/SettingsModel.swift:26/:37`）。
> 所以按原方法跑，六张截图会**全是同一个语言**，而报告会写「六语言已验」——**一次无声的假通过**。
> 实测：收尾那轮按简报原样跑第一次，界面渲染的是**葡萄牙语**（App Group 里当时存的值），不是 `(de)`。
> 真要切界面语言，得写 **App Group 容器里那个 `language` 键**（注意 `defaults write` 要带容器路径，
> 直接 `plutil` 写 plist 会被 cfprefsd 盖掉）。
>
> **但这不影响 §1 的 C1 证据**（`:1296` / `:2342` 那两处仍成立）：那两处测的是
> **`Locale.preferredLanguages` / `Locale.current`**，而 `-AppleLanguages` 落在 NSUserDefaults 的
> **argument domain** 里，`Locale.preferredLanguages` 读它——所以 `preferredLanguages[0] = "zh-Hans"`
> 确实是被它驱动的。**受影响的是「用 `-AppleLanguages` 截界面语言的图」，不是「用 `-AppleLanguages`
> 探 Locale 的值」**，两者是不同的东西，别把这条纠正扩大化。

**所以 Step 6 那张表里所有需要点击 / 相机 / 旋转 / VoiceOver 的项，只有真机能验。**

**2026-09-15 实际跑过一轮静态渲染验证**（用户裁定「把验证扩展到静态渲染能覆盖的屏幕」），结果是：

模拟器状态已复原。六语言截图在 `/tmp/pf-verify/`，MD5 两两不同，**我自己逐张看过**：
德语那张确实是德语（`Kamera nicht verfügbar`、`Lupe`/`Lesen`/`Einstellungen`），

### 5. 方法教训（本会话反复付学费的地方）

**A. 「机制判断对、指向它的指针错」——出现 6 次。** 每次机制结论都经受住了复核，错的全是指针。
第 ⑤ 次尤其说明问题：**刚刚按符号重核过的行号，一小时后又被另一次修复推后了**。
第 ⑥ 次是同一种：`57d7256` 给两处注释各补了理由（+30/−18），硬编码英文审计里刚重核过的
`:321`/`:306`/`:331`/`:330` 又一次全部作废，变成 `:362`/`:347`/`:372`/`:371`。
→ **这恰好证明「追行号」这个动作本身就是错的**：第 ⑤ 次之后我把审计数字更新了一遍，随即又被作废。
处置见上：引符号、附唯一性 grep、行号只当辅助，且已执行完的步骤不再追更。

**B. 全称否定（「没有别的了」「只剩这几处」）必须连**实际跑过的命令和完整输出**一起记录。**
硬编码英文那次有两种**不同**的失败混在一起：第 3 处漏在**结构性盲区**（字面量在 ViewModel 里、
经 `@Published` 中转，只 grep 视图层就看不见），第 4 处漏在**根本没跑那条 grep**（它本来就是视图层
字面量，一查就有）。只写结论的枚举不算枚举。

**C. 增量构建的 `BUILD SUCCEEDED` 什么也没验证。** 它可以在 **0 个 `SwiftCompile` 步骤**下印出
成功——本会话**真的发生过**，并把一位复审者骗过去一次。→ 一律 `clean build` 并**贴出 `SwiftCompile`
条数**；0 就是没编译。

**D. 验证窄于结论。** 出现过多次：`ocr-bench` 不编译被测文件所以「顺序不变」证明不了那个修复；
某报告说「去掉注释只剩 8 行」实际列了 6 行；某次 grep 漏掉了 `addInput`/`addOutput`。
→ 检查的覆盖面必须 ≥ 结论的覆盖面，否则结论要写窄。

**E. 自己产出的证据要先看。** 协调者曾一边断言「两处都会在模拟器上露出」，而自己的截图就摆在旁边
否证它——是 Task 11 复审独立推翻的。断言一个机制之前先读它的定义和调用点。
**这一条在本会话末又犯了一次，形状不同、性质相同**：我警告说「第 3 步那条 grep 不加范围跑会假阳性，
因为它扫进了 `.claude/settings.local.json` 和本计划文件」，实施者则把它归因于「别的会话的未提交改动」。
**两个说法都不是那个机制**：不带 commit range 的 `git diff` 读的是 **工作区 vs 索引**，扫进来的正是
**本会话自己的**未提交计划改动。真正的道理更窄也更简单——**带上范围，这条命令根本不会去读工作区**。
同一对 commit 两种跑法实测：带范围 41 行 → 滤掉注释后 **0**；去掉范围 **278** 行，且它与「你点名了哪
两个 commit」无关（这本身就是破绽：它不是这对 commit 的函数）。**两个人各说了一个自己没核过的机制**，
和第 A 条的指针错是同一个病。→ 机制性的话要么别写，要么写之前先跑。

**F. 简报自己的错也要算账，而且要记下来。** 本会话协调者的简报里有 6 处缺陷：
`for f in en de fr es es it pt`（`es` 写了两遍）、「`applyZoom()` 保持原时序」是**假声明**
（改前它在 `do` 块内，改后变成无条件）、「不要偷偷改」这个措辞直接导致 `cae3009` 要修的假注释、
「私有 `recognize(_:languages:)` 只有一个调用者」实际有两个，以及**修复轮 2 的指令里我自己写的
一条假机制**——「一旦加上 `Task.checkCancellation()`，`error is CancellationError` 就会变成真正
起作用的那一项」。这是错的：`checkCancellation()` 抛错的**条件就是当前任务被取消**，而那正是
`Task.isCancelled` 读的东西，所以到那天两个合取项会**一起**为假，左项依然完全多余。**这条比前四处
更值得记：它不是我写错了措辞，而是我凭空断言了一个我没验证过的机制，实施者照办、缺陷进了 commit，
是复审把它抓回来的。**
→ **简报是产物，也要当产物审。** 尤其是简报里那些「为什么这样做」的论证句——实施者会照抄它们。

**第 6 处，而且是唯一差点造成「假通过」的一处**：静态渲染验证简报把
`-AppleLanguages "(de)"` 写成切界面语言的方法，而**本 App 完全绕过系统本地化**（见 §4 那段警告）。
按简报原样跑，六张「六语言」截图会是**同一个语言**，而验证者会照简报的期望值写「六语言均正常」。
**是实施者自己发现异常才拦住的**——它注意到第一次启动渲染的是葡萄牙语而不是德语，没有把它记成
「参数没生效」了事，而是去读 `LanguageManager.swift` 把机制找了出来，然后换用正确的方法（写 App Group
的 `language` 键）重跑了整个矩阵，并且在报告里把它列为第 1 条顾虑。**这正是「验证者必须自己读代码」
的价值**：简报给了错误的方法，正确的做法是**不照做并说出来**，而不是照着跑完再报「通过」。

**G. 两个 target 的默认隔离不同，读文件看不出来。** `PresbyFriend/` 整棵树同时编进 app 与
`shareextention` 两个 target，但只有 app target 设了 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`。
这是**构建设置**，不是源码性质——只读源码永远发现不了。
